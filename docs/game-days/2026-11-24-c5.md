# Game day C5, 2026-11-24: third full rebuild, first one within the RTO, not clean

## Context

C4 (2026-11-22) rebuilt the platform in 4 h 24 min with 17 defects and failed the 4-hour target. Its
fixes were released before C5 (v0.1.141 to v0.2.2), with four new pieces in the procedure: R1 starts
with an NVMe cryptographic erase, R4SOPS runs just before the tag, R5B takes the first backups of the
rebuilt Pi before R6, and R9 erases the spare after the drill. C5 runs the same scenario on v0.2.2:
the production NVMe (Micron 2200) is removed, the platform is rebuilt on the spare (Samsung 990 PRO)
from the signed GitHub repository and the age-encrypted archives in S3 only, then production comes
back. Drill directory on the laptop: `~/homepi-restore/drill-20261124-1534`.

## Hypothesis, targets and the rule

The rebuilt Pi serves the same platform within the RTO, and production comes back as it left.

| Target | Value |
|---|---|
| RTO | 4 hours, T0 (production off) to R6 PASS |
| RPO | sensor data 1 hour (hourly delta); state and native time series 24 hours |

Rule written before T0: the run is **clean** only if no code changes during the drill; an operation
repeated or done by hand is recorded and also makes it not clean. A run that is not clean is
published with its numbers, and 1.0.0 (docs/versioning.md) waits for the next one.

## Found before T0

The pre-flight checks found that `ansible-playbook` on the laptop PATH was the apt package
(ansible-core 2.20.1) while the Pi and the repository venv run 2.20.11. `release` puts the venv
first, so tag prechecks compared the right versions, but the orchestrator called `ansible-playbook`
directly in R2, R35, R4STORAGE and R4SITE: C5 would have rebuilt the Pi on another runtime than
production. Fixed and released before T0 (v0.2.2: the orchestrator refuses a runtime that differs
from the pin).

Defects 2 and 3 are the same mistake: a verification run right after the system was loaded or
started sees the load, not the platform. Defect 1 is the same class as C4 defect 9: an order in
`site.yml` that production can never show, because every service is already up there.

## Diagnostic mistakes (mine)

- R7: the first block used the `known_hosts` of the first boot, but R3 had restored the production
  host keys (by design): a host key warning, nothing run.
- R7: a host key comparison that read the key type instead of the fingerprint; nothing run.
- R8 blocks that pushed the drill tag to the Pi: production fetches tags from GitHub and had already
  deployed v0.2.3 (step 4 of R8 was unnecessary; the runbook now says so).

## What went well

- The cryptographic erase, R5B and R4SOPS-before-the-tag worked on their first real run. Because
  R4SOPS now follows R4SITE, the fix for defect 1 went in with no commit to reorder.
- The orchestrator recorded every phase; the RTO and RPO above come from it, not from notes.
- Identities kept again: no certificate re-issued, 7 devices back on both systems.
- The spare left the drill erased (R9, second run on the hardware).
