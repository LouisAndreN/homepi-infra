# Game day 2026-11-07: reboot after the storage change

## Context

B1 moved Loki to its own XFS volume (`lv-loki`), made GitOps verify the fstab entries and the Btrfs
mount units (role `storage`, v0.1.35 to v0.1.37) and added `nofail` on `lv-loki` with
`RequiresMountsFor` on Loki. fstab, mount ordering and unit dependencies are only proven by a boot.
The Pi had been up since 2026-10-28, ten days without a reboot.

## Hypothesis

After a reboot with no manual action, every mount is in place, Loki starts on `lv-loki` after its
mount, and `systemctl is-system-running` reports `running`.

## Preconditions, checked by the test before rebooting

| Check | Value |
|---|---|
| Boot chain vs the last successful boot | First attempt stopped by the test: `/boot/firmware/vmlinuz` and `initrd.img` rewritten on 2026-11-06 06:47 by unattended-upgrades (`linux-firmware-amd-graphics` triggered initramfs-tools, flash-kernel copied the result). Accepted after proof: vmlinuz identical to the running 6.8.0-1065-raspi, initrd built for that kernel with dm-crypt, `.bak` copies equal to the last booted set |
| `cmdline.txt`, `config.txt`, `/etc/crypttab` | unchanged since boot |
| Real unlock path | the `/etc/crypttab` keyfile opens `cryptdata` (`cryptsetup --test-passphrase`). The root is not encrypted: the initrd crypttab only holds swap, `cryptdata` is opened by systemd after the initramfs |
| GitOps run in progress | none |

## Run 1, 14:27 JST: FAIL

SSH back after 152 s, startup 30.4 s, `cryptdata` unlocked in 8.3 s, all seven mounts correct, Loki
active after `var-lib-loki.mount` and ingesting. `systemctl is-system-running`: `degraded`.

| Seconds since boot | Event |
|---|---|
| 17.7 | mosquitto starts; its mTLS listener binds 192.168.200.1 |
| 18.3, 19.3 | mosquitto exits 1 twice, start limit reached (`Restart=on-failure`, 100 ms) |
| 19.3 | step-renew (timer catch-up) calls step-ca: connection refused, `Restart=no` |
| 19.7 | step-ca serves HTTPS |
| 20.2 | 192.168.200.1 configured on the access point interface |
| 20.6 | hostapd `AP-ENABLED` |
| 21.1 | telegraf: mqtt_consumer refused on 127.0.0.1:1883, the agent exits |

Root cause: a unit being "started" is not the service being usable. Ordering on `network.target` or
`step-ca.service` guarantees neither the address nor a serving CA. Ten days of uptime had hidden the
three races; a power cut would have left IoT collection down until someone restarted it by hand.

## Fix, v0.1.40 (role `service_ordering`)

Each service waits, with a bound, for the condition it really needs:

- mosquitto: `ExecStartPre` waits up to 60 s for 192.168.200.1 on the access point interface,
  `After=hostapd.service`; `Restart=on-failure` every 5 s, at most 10 times in 5 minutes, as a net.
- telegraf: `After=` and `Wants=mosquitto.service`, then retries every 10 s without limit.
- step-renew and step-renew-mosquitto: `ExecStartPre` waits up to 60 s for step-ca `/health` over
  verified TLS.

## Not proven by this game day

- The step-renew fix: its timer had just run, so there was no catch-up at boot. Proven only by a
  manual start (success).
- Loki `/ready` answered 503 for about 3 to 4 minutes after boot, while ingestion worked and the
  rings were ACTIVE at 22.9 s. WAL replay took 0.9 s. Cause not found (known limits).

## Follow-ups

  or initramfs update (roadmap B10).
- Loki ring on the `inmemory` kvstore, then measure `/ready` again (roadmap B5).
