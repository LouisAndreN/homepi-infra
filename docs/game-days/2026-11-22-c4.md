# Game day C4, 2026-11-22: second full rebuild, recorded by the orchestrator

## Context

C3 (2026-11-21) rebuilt the platform on a spare disk in 6 h 30 min with 44 defects. Between the two
drills: R3.5 as code, a static LAN address, write checks, the restore orchestrator
(`scripts/restore/homepi-restore`, which records every phase in `timeline.tsv`) and an hourly
sensor delta for a 1 h RPO. C4 runs the same scenario: the production NVMe (Micron 2200) is
removed, the platform is rebuilt on the spare (Samsung 990 PRO) from the signed GitHub repository
and the age-encrypted archives in S3 only, then production goes back (R8). Drill directory on the
laptop: `~/homepi-restore/drill-20261122-1452`. Public write-up: article 20 of the series.

## Hypothesis and targets

The rebuilt Pi serves the same platform (7 ESP32s reconnected without re-enrolment, data flowing,
no alert firing) within the RTO, survives a controlled reboot, and production comes back as it left.

| Target | Value |

| RTO | 4 hours, T0 (production off) to R6 PASS (same target as C3) |

## Deviations from the procedure

Each one restores the state the fixed procedure produces; none bypasses a check.

1. R1/R2: bootstrap resolved drop-in written by hand (defect 6).
2. R6: `systemctl start dnsmasq` once. The release precheck runs the verify-only network role,
   which refused v0.1.143 because dnsmasq was down, the very failure v0.1.143 fixes. The next
   controlled reboot proved the fix.
3. R6: `chmod 0755 /mnt/data /mnt/data/backups` (defect 16). `@iot-archives` and `@personal` were left
   0700, to be compared with production.

Operations run by hand, by the same units as their timers: the GitOps check, the three first
backups (state 1 s, native 42 s, line protocol 95 s) and the off-site upload (26 s, about 700 MB).

## Diagnostic mistakes (mine)

- A placeholder address in a block, and a branch built from `origin/main` that diverged from the
  local `main`.
- A gate on the last command of a remote script (`systemctl is-active` exits 3 on a failed unit).
- A FAT timestamp probe written and read in the same boot, which cannot show a timezone change.
- A gate on the last element of a path instead of the whole path (`/mnt/data` was 0700 too).
- Defect 13 first blamed on the locale; the kept log showed the SSH master.
- A push of `main` to the production bare repository, which relays to GitHub: four laptop commits
  reached GitHub `main` without the typed MERGE. Tags alone go to `pi` from now on.
- Waits of 15 to 20 minutes for GitOps: release to production takes up to 30 minutes (precheck of
  the whole `site.yml`, 10-minute apply timer, the hourly check holding the lock).

## Open questions

- `homepi-alloy-check` failed twice in R6 on production and passed when run alone. The suspected
  cause, Alloy restarted by an apply, is refuted: Alloy had run since boot (19:32:39). Next failure:
  keep its full output.
- The sensor data collected by the rebuilt Pi (15:01 to 19:30) stays on the spare, but its hourly
  deltas are in S3 and could be replayed into production with `homepi-r5-deltas`. Not done.

## Lessons

1. A restore is finished when the restored system is protected, not when it serves: four hours
   without a backup of the new system is the most fragile moment of the incident (defect 15).
2. A controlled reboot of the rebuilt system is part of the drill: it found three defects, two of
   them latent in production.
3. A check that discards its output reports a symptom forever (defect 13: "no drift report" twice).
4. A drift guard can block the deployment of the fix for the drift it detects; the answer is to
   restore the service as an operation, then deploy, never to bypass the guard.
5. Timestamps on FAT are not evidence; content hashes are.
6. The core held again: identities kept, no certificate re-issued, production back in 5 seconds.
